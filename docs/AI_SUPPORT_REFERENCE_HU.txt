================================================================================
Keretrendszer-felismerés (FRAMEWORK, ESX_CORE, QB_CORE)
================================================================================

Mérvadó forrásfájlok
  bridge/esx/config_defaults.lua   – e_core_apply_esx_config()
  bridge/qb/config_defaults.lua     – e_core_apply_qb_config()
  bridge/framework_config.lua       – választás, ESX_CORE / QB_CORE, hívja az
                                      apply függvényeket
  fxmanifest.lua → shared_scripts → a fenti három fájl ebben a sorrendben

Logika (rövid)
  Lokálisan: esx_started = GetResourceState('es_extended') == 'started',
  qb_started ugyanígy a 'qb-core'-ra. ConVar: e_core:framework = auto | esx | qb
  (alap: auto).

  Egy core + auto → az a keretrendszer; apply + FRAMEWORK / ESX vagy QBCore /
  eCore / Config alapértékek.

  Két core + auto → error (állítsd a ConVart esx vagy qb-ra).

  Két core + esx|qb kényszer → apply a választott ág + figyelmeztető log; a másik
  core resource akkor is futhat, de ESX_CORE / QB_CORE **csak a választott ág**
  szerint true (a nem választott bridge guardjai nem futnak).

  Semmi core induláskor → figyelmeztető log, FRAMEWORK = nil, eCore = {},
  Config = {}, ESX_CORE = false, QB_CORE = false.

  A bridge/esx/*.lua és bridge/qb/*.lua (shared, client, server, events) nagy
  része if ESX_CORE / if QB_CORE guarddal fut. A globális FRAMEWORK string a
  bridge/main.lua exportján megy ki:
    exports("getFrameWork", function() return FRAMEWORK end)

Consumer
  imports/core.lua: FRAMEWORK = exports.e_core:getFrameWork()
  (Az e_core resource-nak a consumer előtt kell elindulnia; lásd README ensure
  sorrend.)

Kettős core egy szerveren
  **Támogatott modell:** egy FiveM szerveren **egy** legacy keretrendszer fut –
  **ESX vagy QB**, nem mindkettő párhuzamosan.

  **Ha mégis mindkét core `started`:** `e_core:framework=auto` → indulás
  **megáll** (Lua error üzenettel). Kényszerített esx|qb esetén egy aktív bridge
  ág; operátori feladat a felesleges core eltávolítása. Részletek:
  docs/FRAMEWORK_CONFIG_REFACTOR_TERVEZES_HU.md (6. szakasz: ConVar).

QBox / README vs. kód
  A README említhet QBox-ot. Az e_core Lua felismerése **`qb-core`** resource
  névre és erre az exportra épül: `exports['qb-core']:GetCoreObject()` → globális
  **`QBCore`** (`bridge/qb/config_defaults.lua` → `e_core_apply_qb_config`).

  **QBox legacy módban** a kompatibilitási réteg továbbra is a **`qb-core`**
  resource nevet használja (nem külön `qbx_core` néven fut a detektált core), és
  a mag objektum neve **`QBCore`** marad – ezért a fenti `GetResourceState(
  'qb-core')` és `GetCoreObject()` hívás tipikusan **működik** legacy QBox
  szerveren is.

  Ha a szerver **nem** legacy (más resource név / más export), a bridge nem
  ismeri fel automatikusan; ensure név és export **szerverenként** egyeztetendő a
  kóddal vagy külön fork-illesztéssel.

Nem ez választ keretrendszer között
  Az ox_inventory, qs-inventory, avp_grid_inventory stb. GetResourceState
  flagjei a standalone/overrides/<név>/config.lua fájlokban vannak; ezek
  kiegészítő integrációt jelölnek, nem ESX helyett QB-t.

ESX bridge (bridge/esx)
================================================================================

Előfeltétel
  ESX_CORE == true (lásd „Keretrendszer-felismerés”). Ha false, az alábbi
  fájlokban lévő eCore: metódusok nem töltődnek be.

Mérvadó forrásfájlok (fxmanifest sorrend)
  bridge/esx/config_defaults.lua – shared; e_core_apply_esx_config (lásd fent)
  bridge/esx/shared.lua           – shared + client + server (kétszer fut a
                                    manifest miatt); convertPlayer,
                                    convertItems
  bridge/esx/client.lua           – client; UI, progress, játékos, inventory
                                    olvasás kliensen
  bridge/esx/server.lua           – server; xPlayer, pénz, inventory írás,
                                    callbacks, parancsok
  bridge/esx/events/client.lua    – ESXEvents tábla: sharedEvents + ESX

                                    továbbítás

  bridge/main.lua                 – if ESX_CORE: RegisterNetEvent minden
                                    ESXEvents[] elemre

    Inicializálás + Config.maxInventoryWeight / slots, Config.fields (ESX
    mezőnevek: count, stb.), Config.itemBox, Config.imagePath, stb.

  shared.lua

    eCore:convertItems(items) – item kulcs lower, image, isUnique/isWeapon
    alapértékek; REGISTERED_ITEMS nélküli item lista egységesítéséhez használt.

  client.lua (ESX API-kra támaszkodik)
    triggerCallback → ESX.TriggerServerCallback
    sendMessage → ESX.ShowNotification
    drawText / hideText → ESX.TextUI / ESX.HideUI
    progressbar → ESX.Progressbar (animation.dict / anim átalakítás); cancel
    → ExecuteCommand("cancelprog")
    isLoggedIn → ESX.PlayerLoaded
    getInventory(playerData) → playerData.inventory
    getRegisteredItems() → REGISTERED_ITEMS ha van, különben convertItems(
      ESX.GetPlayerData().inventory)
    getPlayer(newJob) → convertPlayer(ESX.GetPlayerData(), …)
    getAccounts, canInteract, jármű: setFuelLevel (LegacyFuel komment), vehicleKeys
    (komment), setVehicleProperties, setVehiclePropertiesFromNetId (hurok +
    SetBoatAnchor), deleteVehicle, getClosestVehicle

  server.lua
    createCallback → ESX.RegisterServerCallback
    createUsableItem → ESX.RegisterUsableItem
    sendMessage / drawText / hideText → esx:showNotification, ESX:TextUI,
    ESX:HideUI kliens események
    addMoney / removeMoney / getAccounts – xPlayer vagy source szám →
    GetPlayerFromId
    getInventory / getInventoryWeight / getPlayerMaxWeight – xPlayer
    addItem – xPlayer.addInventoryItem(item, count) – slot/metadata nélkül
    removeItem – xPlayer.removeInventoryItem(…, metadata, slot)
    removeItems – tábla iteráció, item.amount mező
    getRegisteredItems – REGISTERED_ITEMS ha van, különben convertItems(
      ESX.Items); függvényen belül újra ESX = exports['es_extended']:
      getSharedObject()
    getPlayer(playerId) – convertPlayer(ESX.GetPlayerFromId)
    itemBox – TriggerClientEvent('inventory:client:ItemBox', …) ha
      Config.itemBox
    addCommands → ESX.RegisterCommand

Esemény-bridge (ESX → e_core)
  Kliens (bridge/esx/events/client.lua), ESXEvents a bridge/global/events/
  client.lua sharedEvents tömbjére épül, majd bővül:
    esx:playerLoaded      → ESX.PlayerLoaded = true; convertPlayer;
                            TriggerEvent('e_core:onPlayerLoaded', …)
    esx:onPlayerLogout   → ESX.PlayerLoaded = false;
                            TriggerEvent('e_core:onPlayerUnload', playerId)
    esx:setJob            → TriggerEvent('e_core:onJobUpdate', job)
  Szerver (bridge/esx/events/server.lua):
    esx:playerLoaded      → convertPlayer(xPlayer);

                            playerId, isNew)
    esx:playerDropped     → TriggerEvent('e_core:playerUnload', playerId)

Felülírás (README szerződés)
  A fájlok tetején komment: módosítás helye standalone/overrides/…, ne közvetlen
  bridge/esx szerkesztése frissítésbiztos testreszabáshoz.

Fontos megjegyzések (hibakeresés / portolás)
  Az ESX build (legacy vs. új notify/TextUI/Progressbar) eltérhet – ha üres
  vagy hibás UI, ellenőrizd az es_extended verziót és az ESX hívásokat ezekben
  a függvényekben.
  Kliens getRegisteredItems alapértelmezésben játékos inventoryból dolgozik;
  szerveren ESX.Items – ox_inventory vagy override esetén a globális
  REGISTERED_ITEMS és a standalone override réteg a mérvadó (lásd server
  loop; súly/slot közös logika: „Global bridge” szekció).
  A jármű / kulcs / üzemanyag részek részben kikommentelt példák; éles
  integrációhoz override kellhet.

Global bridge (bridge/global)
================================================================================

Szerep röviden
  Keretrendszer-független **eCore** metódusok és közös **NetEvent** alapok.
  **Nincs** if ESX_CORE / if QB_CORE guard: a fájlok mindig betöltődnek
  (shared + client vagy server oldal szerint a manifest szerint).

Mérvadó forrásfájlok (fxmanifest sorrend, összefoglalva)
  bridge/global/shared.lua         – shared, majd client + server is;
                                      inventory súly / slot / egyeztetés
  bridge/global/client.lua         – client; ox_target export wrapper
  bridge/global/server.lua         – server; eCore:createVehicle
  bridge/global/events/client.lua  – sharedEvents tömb kezdete +
                                      e_core:methodCaller
  bridge/global/events/server.lua  – sharedEvents kezdet (**nem** tartalmaz
                                      `e_core:createVehicle` NetEventet – G audit)
  bridge/global/callbacks/server.lua – `e_core:createVehicle` **csak** szerver
                                      callback (`createCallback` + forrás ellenőrzés)
  bridge/main.lua                  – csak ESXEvents / QBEvents regisztráció;
                                      a global sharedEvents elemei **uganarra
                                      a táblára** kerülnek rá (lásd lent)

shared.lua (eCore metódusok, Config.fields és REGISTERED_ITEMS)
  **Cél:** keretrendszer-független **súly / slot / „befér-e”** logika a
  `playerData` + `getInventory(playerData)` alapján. A QB alap inventory
  slotonként tárol; a **több stackből adódó összesített mennyiség** recept /
  anyagellenőrzéshez a **`getAmountOfItems(inventory)`** használata javasolt
  (itemnév → összegzett `amount` minden nem üres slotban). Közvetlenül csak
  egy slotot nézni **alábecsülheti** a készletet (pl. két×5 víz → 5).

  getInventoryWeight(playerData) – ha van playerData.weight, azt adja;
    különben getInventory + Config.fields.count/weight + Config.
    totalStackWeight szerinti összegzés.
  canSwapItems(swappingItems, itemData, playerData) – súly + szabad slot +
    unique item logika; a `swappingItems` levonását **végigjárja** az
    inventory sorait (több stack esetén is); REGISTERED_ITEMS[…] olvasás;
    false okok: too_heavy, not_enough_space.
  canCarryItem(itemData, playerData) – kapacitás + slot igény (unique vs.
    meglévő stack); **nem** helyettesíti a teljes recept-lista ellenőrzést –
    összetett „van-e minden alapanyag” esetén `getAmountOfItems` + saját
    összehasonlítás vagy `canSwapItems` receptút.
  countFreeSlots(inventory) – Config.maxInventorySlots minus occupied.
  getItemWeight(itemName, metadata) – REGISTERED_ITEMS + ammo / components /
    metadata súly kiegészítés.
  getFirstSlotByItem(inventory, itemName) – első nem üres slot indexe az
    adott névhez (nem összegzett mennyiség).
  getAmountOfItems(inventory) – **vissza:** tábla `{ [itemName] = összDarab }`
    minden slot `Config.fields.name` / `count` szerint összeadva; recepthez /
    „van elég X” kérdéshez **ez** a megfelelő primitív.
  getRegisteredItem(name), isReady() → `CORE_READY` globális; értékét a
    `hf.awaitItemRegistryReady` állítja a client/server `main.lua` induló szálában
    (siker / timeout után).

  **QB + ox_inventory:** a fenti súly/slot számítás a **bridge által adott**
  inventory táblára és `Config.maxInventoryWeight` / `REGISTERED_ITEMS`
  súlyokra épül. Ox alatt a valós kapacitás és slot szabályok gyakran **ox
  exportokon** mennek át. Érdemes a **`standalone/overrides/ox_inventory`**
  (vagy a használt stack szerinti override) alatt **`eCore:canSwapItems`** és
  **`eCore:canCarryItem`** (és szükség szerint kapcsolódó metódusokat)
  **felülírni**, hogy az ox legyen a forrásigazság – a global `shared.lua`
  maradhat fallback / nem-ox szerverekre. A repó ox override mappája **jelenleg**
  főleg `getRegisteredItems` / `convertItems`-et tartalmaz; a capacity-függő
  függvények ox-hoz kötése **ugyanide** másolható a bridge komment szerinti
  mintában. Példa más override-ban: `standalone/overrides/avp_grid_inventory/`
  (`canSwapItems`, `canCarryItem`).

  **Függőség:** canSwapItems / canCarryItem / getItemWeight feltételezi, hogy
  a REGISTERED_ITEMS tábla **kulcsonként** elő van készítve (kisbetűs név,
  isUnique mező). Üres vagy hiányzó item → runtime hiba lehet. Előállítás:
  client/main.lua és server/main.lua ciklus eCore:getRegisteredItems()-ig
  (framework-specifikus implementáció az ESX/QB bridge-ben + override).

client.lua (ox_target)
  Minden függvény közvetlenül továbbít az exports.ox_target:* hívásokra
  (disableTargeting, addGlobalOption, removeGlobalOption, zónák, model,
  entity, ped, player, vehicle, stb.). **Függőség:** ox_target resource;
  hiányában hiba induláskor.

server.lua
  eCore:createVehicle(pos, model, vType, props) – jármű létrehozás szerveren
    (CreateVehicleServerSetter ha van + vType string, különben CreateVehicle),
    rendszám / network owner várakozás, netId, majd TriggerClientEvent(
    'e_core:methodCaller', owner, 'setVehiclePropertiesFromNetId', netId,
    props). Visszaadás: netId, vehicle entitás.

callbacks/server.lua
  eCore:createCallback('e_core:createVehicle', …) – cb(netId, serverId);
    a createCallback implementáció ESX/QB bridge-ben van (RegisterServerCallback
    / QBCore callback).

Események és sharedEvents összefűzése
  bridge/global/events/client.lua: **sharedEvents = {}**, majd
    e_core:methodCaller → **whitelist** (`methodCallerAllowed`), csak engedélyezett
    `method` esetén `eCore[method](eCore, …)`; elutasításkor `print` + `cLog`.
  bridge/esx/events/client.lua (ha ESX_CORE): **ESXEvents = sharedEvents**
    (ugyanaz a tábla referencia), majd további insertek.
  bridge/qb/events/client.lua (ha QB_CORE): **QBEvents = sharedEvents**
    (ugyanaz a tábla referencia QB-nél is).
  bridge/main.lua: a kiválasztott keretrendszer ESXEvents vagy QBEvents
    elemeire RegisterNetEvent – így a **methodCaller** és a framework saját
    eseményei **egy** táblában vannak, betöltési sorrend: global → esx → qb
    (manifest szerint).

  Szerveren: bridge/global/events/server.lua ugyanígy **sharedEvents** kezdet;
    ESX/QB server events ugyanerre a táblára épülnek. (`e_core:createVehicle`
    kliens hívása: **callback**, lásd callbacks/server.lua + NET_EVENTS doksi.)

Megjegyzés (e_core:createVehicle – csak callback)
  A `e_core:createVehicle` **nem** `RegisterNetEvent` a sharedEvents táblában
  (eltávolítva G audit miatt). Jármű: **`e_core:createCallback('e_core:createVehicle', …)`**
  (`bridge/global/callbacks/server.lua`) + `hf.isValidPlayerSource(source)`.

Felülírás
  Ugyanaz a bridge komment a shared.lua tetején: **standalone/overrides/**.

Fontos megjegyzések
  A global shared **erősen támaszkodik** REGISTERED_ITEMS-re és Config.fields-
  re; inventory override vagy más mezőnév esetén a bridge config + override
  együtt érvényes.
  ox_target és oxmysql/ox_lib mellett a global client **további** kemény
  függőség az ox_target felé.

0. Mit és milyen formában tartalmazzon? (mérvadó szerkezet)
================================================================================

Cél: az AI **ne találjon ki** nem létező exportot, és **lépésről lépésre** tudja
követni, melyik fájl melyik szerződést valósítja meg (különösen ritka
inventory-nál).

--- A) Formátum (egy API / egy funkció blokk) ---

Minden **publikus** felületnél (exports.e_core + fontosabb eCore: metódusok)
érdemes ugyanazt a mintát használni (soronként vagy rövid táblázat):

  Név:              pl. eCore:addItem  vagy  exports.e_core:getLabor
  Oldal:            client | server | mindkettő
  Keretrendszer:    ESX | QB | közös / global (ha eltér, két blokk)
  Szerep (1–3 mondat): mit csinál a consumer szempontjából; mikor hívjam.
  Paraméterek:      név, típus (lua), kötelező?, magyarázat
  Visszatérés:      típus / tábla mezők; multi-return (ok, err) felsorolása
  Hibák:            string konstansok (pl. not_found_metadata), mikor jönnek
  Megjegyzés:       async, source, xPlayer vs playerData forma
  Forrás:          fájl: sor régió vagy fájlnév (grep-barát)

A **név + oldal + keretrendszer** hármas elengedhetetlen, mert ESX/QB-nél az
eCore ugyanazon metódus neve mögött más típusú játékos/objektum lehet.

--- B) Mit tartalmazzon a fájl nagyobb blokkokban ---

1) **Architektúra** – könyvtárak szerepe + „hol ne nyúlj” (bridge vs overrides).
   ESX: „ESX bridge”; QB: „QB bridge”; közös logika: „Global bridge”; kliens
   resource: „Client resource” szekció ugyanebben a fájlban.
2) **Indulási szerződés** – ensure sorrend, REGISTERED_ITEMS / ready, tipikus
   nil / végtelen várakozás okok (röviden, linkekkel a forrásra). Keretrendszer-
   felismerés: ugyanebben a fájlban a „Keretrendszer-felismerés” szekció.
3) **Export API** – csak a ténylegesen exportált függvények; copy-paste név.
4) **eCore API** – táblázatos vagy ABC rend; ahol ugyanaz a név, ott altípus
   (ESX server vs QB server).
5) **Adapter / inventory** – külön fejezet: lentebb (0.1) + szekció 4.
6) **GYIK** – valós kérdés → rövid válasz + fájlhivatkozás.

--- C) Mi legyen később külön fájlban (opcionális) ---

Ha a .txt túl hosszú lesz: **docs/PUBLIC_API.md** (csak táblázat + link a
részletes magyarázatra), vagy **inventory mátrix** (Tier1/2) – a .txt-ben elég
a link + 10 sor összefoglaló.

0.1 Ritka „XY inventory” integráció – mitől tud válaszolni az AI?
================================================================================

Az AI akkor tud **konkrét** integrációs választ adni, ha a dokumentumból (és a
repó mintájából) összeáll ez a **hármas**:

(1) **Szerződés (contract)** – mit vár az e_core az inventory felől?
    - Milyen **adatstruktúra** a „játékos inventory” a bridge-ben (slot, count,
      metadata mezők neve)?
    - Mely **eCore** hívások érintik: getInventory, addItem, removeItem,
      removeItems, getPlayerMaxWeight, getRegisteredItems, getRegisteredItem,
      shared: canCarryItem, getItemWeight, stb.
    - A **hibamodel**: mit ad vissza „tele van” / „nincs item” (string vagy nil)?

(2) **Illesztési pontok (hook lista)** – mit kell megírni / másolni?
    - Új mappa: standalone/overrides/<xy_inventory>/
      config.lua, shared.lua, client.lua, server.lua – mit exportál az XY
      resource (FiveM exports / események)?
    - Hol hívódik az override: fxmanifest **standalone/overrides/** glob.
    - **Mintapár**: melyik létező override a legközelebbi (ox_inventory,
      qs_inventory, example_custom_inventory) – a doksi nevezi meg.

(3) **Környezeti tények** – a felhasználó kérdéséből vagy fixen a GYIK-ből:
    - Keretrendszer: ESX vagy QB.
    - Az XY resource **hivatalos neve** (ensure név) és **export API** 2–3
      mondatban (ha nincs a doksidban, az AI csak általános irányt ad – ezt
      írd le a GYIK-ben is).

**Gyakorlati sablon** egy új inventory GYIK bejegyzéshez (másold be kitöltve):

  Inventory resource neve (ensure): …
  Dokumentáció / exportok (URL vagy felsorolás): …
  Legközelebbi e_core minta override: …
  ESX/QB: …
  Különleges viselkedés (stack, fegyver, metadata): …
  Ismert bukkanók (pl. async addItem): …

Ha ez megvan a GYIK-ben vagy egy külön **docs/inventory_xy.txt**-ben, az AI a
kérdésre: „tudom-e integrálni az XY-t?” → **igen/nem + lépések + fájlnevek**,
nem pedig általános blabla.

0.2 Központi ügyfél-link (AI tudásbázis) – hová és milyen szerkezetben
================================================================================

Cél: az ügyfél **egy URL-t** kapjon; onnan **szkriptenként**, azon belül
**területenként** (API, telepítés, inventory, hibakeresés…) lehessen ugrani.
Az AI (és az ember) **másolható linkkel** hivatkozzon egy konkrét oldalra.

Forrás vs. publikáció (mérvadó elv)
  - **Igazság forrása:** a Git repó `docs/` + a resource saját README / *.md /
    `*_HU.txt` (verziókövetés, PR review).
  - **Ügyfélnek adott központi index:** legyen **külön**, böngészőből elérhető
    (lásd opciók lent). Ne csak „nyers GitHub mappa”, ha lehet: **egy index
    oldal** (tartalomjegyzék), rövid magyarázattal, mit hova tettünk.

Hol hostoljuk? (választás – egyet válassz stratégiának)
  A) **GitHub Pages** egy **publikus** `docs-*` vagy `eco-wiki` repóból
     (MkDocs / Docusaurus / sima HTML index). Előny: ingyenes, linkelhető,
     verziózott build. Hátrány: ami publikus, az **látható** (ne legyen benne
     escrow / titkos logika).
  B) **GitBook, ReadMe.com, Notion** stb. – szép nav, jogosultság, gyors
     szerkesztés. Hátrány: költség / zárolt export / kevésbé „git-native”.
  C) **Saját domain** (`docs.például.hu`) – statikus site ugyanabból a
     publikálható markdownból (CI: push → deploy). Előny: márka, egy helyen
     minden eco termék.
  D) **Tebex / Keymaster leírás** – csak **rövid** + link a fenti A/B/C-re;
     a hosszú technikai anyag ne a termékoldalba legyen zsúfolva.

Javasolt **URL-szerkezet** (minta – a domain mindegy):

  https://docs.example.com/                    → főindex (minden resource)
  https://docs.example.com/e_core/             → e_core áttekintés + verzió
  https://docs.example.com/e_core/install/   → telepítés, ensure sorrend
  https://docs.example.com/e_core/api/       → exportok, eCore, hibák
  https://docs.example.com/e_core/inventory/ → override, ritka integrációk
  https://docs.example.com/eco_crafting/     → másik szkript, ugyanígy bontva

A **főindex** legyen egyetlen „linkgyűjtemény”: táblázat: Oszlopok =
**Resource** | **Rövid leírás** | **Telepítés** | **API / AI referencia** |
**GYIK / integráció**.

Szinkron szabály
  - Repóban lévő `AI_SUPPORT_*` / mérvadó szövegek **build input**; ügyfél oldal
    **deploy** (manuális másolás vagy CI). Verzió a resource `fxmanifest`
    `version` mezőjével egyezzen az indexen (vagy changelog link).

imports/locale.lua (shared)
  Szerep
    Egységes **fordítás** a `locales` táblán (betöltés: `locales/*.lua`) és
    `Config.locale` alapján.
  Globálisok
    `locales` tábla (üres kezdet, a locale fájlok töltik); `translate(str, …)`;
    `translateU(str, …)` – első betű nagy (csak a szó elején).
  Paraméterek: translate / translateU
    str: string, kulcs a locale táblában.
    …: opcionális, `string.format` argumentumok, ha a fordítás tartalmaz `%s` /

  Visszatérés

    Hiányzó kulcs: **visszaadja az eredeti str** (nincs throw).

  Megjegyzés

    függvénye (config → locales/*.lua).

imports/utils.lua (shared)
  Szerep
    Debug és kliens-oldali **kényelmi** segédek (blip, model/anim/ptfx load,
    feltételes console log).
  Függvények (globálisok, export nélkül)
    print_r(t)           – rekurzív tábla kiírás a konzolra (körreferencia
                         védelem cache-sel).
    createBlip(coords, sprite, color, scale, name)
                         – vec3-szerű coords; vissza: blip handle.
    animDictLoader(dict) – max ~20×100 ms próba; false ha nincs dict vagy nem
                         tölt be.
    modelLoader(model)   – hasonló próbahurok; false ha invalid / timeout.
    fxLoader(dict)       – RequestNamedPtfxAsset + várakozás (végtelen ciklus
                         amíg nem tölt be – resource stop nélkül óvatosság).
    cLog(k, v, level)    – ha `Config.debugLevel` hiányzik vagy < 1: no-op;
                         egyébként **szint szűrés** (`level` > `Config.debugLevel`
                         → no-op).
                         **Általános ág:** tábla vagy függvény `v` → `print_r(v)`;
                         egyéb típus → `DEBUG k -> v` sor.
    cLog – **severity (egy soros) mód**
      Ha `v` **pontosan** a következő string egyike: `error`, `warning`, `info`,
      `debug` **és** a harmadik argumentum (`level`) **szám**, akkor egy **színezett
      egy soros** üzenet jön ki: `[ERROR]`, `[WARNING]` stb. + `k` szöveg
      (FiveM `^1` / `^3` / `^2` / `^5` színkódok).
      **Cél:** `server/db.lua`, `hf.mysqlAwait` és hasonló hívások egységes,
      jól látható konzol kimenete.
      **Figyelem:** ha a második paramétert **adatként** szeretnéd logolni és
      véletlenül ezek egyike lenne (`'info'` stb.), válassz más szót (pl.
      `'info_text'`), különben severity-ként értelmeződik.
  Megjegyzés
    `cLog` a bridge/main.lua-ban is használatos (eseményregisztráció log); a
    `Config.debugLevel` standalone configban állítható.

imports/discordlog.lua (server)
  Szerep
    **Discord webhook** üzenet-építő: több embed, mezők, `PerformHttpRequest`
    POST JSON-nel. **Consumer** resource-ok a manifestben include-olhatják
    (pl. `@e_core/imports/discordlog.lua` **server_scripts**-ben, az **e_core**
    utáni ensure mellett). Belső e_core hívó a repóban opcionális; főleg külső
    eco szerverlog / admin értesítés.
  Függőség
    `local hf = eCore.helper` – trim; az e_core manifestben a fájl a
    **bridge/main.lua** után van, így `eCore` / `hf` a chunk betöltésekor érvényes.

  Név: createDiscordLog(webhook, botName?, opts?)
    Oldal: server
    Keretrendszer: közös (eCore.helper)

    Paraméterek
      webhook: string, **https** és tartalmazza az `/api/webhooks/` részt
               (Discord / canary / régi discordapp host – tipikus webhook URL).
               Érvénytelen → **false** + opcionális `cLog` egy sorban.
      botName: opcionális string; alap felhasználónév: `'ECOBOT'` (max hossz
               csonkolva).
      opts: opcionális tábla:
        defaultColor   – szám / név / `#RRGGBB` – új embed alap színe
        avatar_url     – webhook kérés szintű alap avatar URL (`reset` után is)
        onError        – `function(statusCode, responseBody)` – HTTP nem 2xx

    Visszatérés
      **self** tábla (építő), vagy **false** (érvénytelen webhook).

    Metódusok (építő)
      reset()              – üzenet törlése; embed lista üres; `embedId` nullázva.
      putEmbed()           – új rich embed a sor végére (több embed lánc).
      content(s)           – top-level `content` (max ~2000 karakter, csonkolva).
      username(s)          – webhook felhasználónév felülírás egy küldéshez.
      avatarUrl(s)         – webhook avatar URL felülírás / törlés (üres → nil).
      title(s), description(s), footer(s)
      url(s)               – embed `url` (pl. dokumentum link).
      color(c)             – név: `yellow`, `green`, `red`, `orange`, `blue`,
                           `purple`, `grey`/`gray`, `teal`, `white`, `black`;
                           vagy **decimális** szín; vagy **`#RRGGBB`** / `RRGGBB`.
      putField(name, value, inline?, codeBlock?)
                           – alapból érték **kódblokkban** (``` … ```), mint a
                           korábbi viselkedés; **codeBlock = false** → nyers szöveg
                           (hosszabb szöveg / URL).
      timestamp(unix?)     – embed ISO időbélyeg; param nélkül `os.time()`.
      author(name, url?, iconUrl?)
      thumbnail(url), image(url)
      clearFields()        – aktuális embed `fields` ürítése; **return self**.
      appendFields(list) – tömb: `{ { name, value, inline?, codeBlock? }, … }`;
                           sorrend megmarad; **return self**.
      embed(opts)         – egy táblából kitöltés; **opts.newEmbed = true** → előbb
                           új embed (`putEmbed`); egyébként `_ensureEmbed`. Kulcsok
                           (mind opcionális, ha meg vannak adva): **username**,
                           **avatarUrl**, **content**, **color**, **title**,
                           **description**, **url**, **footer**, **timestamp**
                           (`true` = aktuális idő), **author** `{ name, url?, icon_url? }`,
                           **thumbnail**, **image**, **fields** (lásd `appendFields`).
                           **return self** (lánc: `log:embed({…}):send()`).
      alert(opts)         – gyors állapot: **level** = `error` / `warning` / `info` /
                           `ok` (alap: `error`) → előre definiált **color**; opcionális
                           **content**, **title**, **description**, **footer**, **fields**.
                           Nem nyit új embedet (kompatibilis a „zöld váz + piros hiba”
                           mintával). **return self**.
      send(doneCb?)        – POST; **üres** `content` és **nincs embed** → nem
                           küld, `cLog` (2-es szint, ha engedélyezett), callback
                           ha van: `doneCb(false, 0, 'skipped_empty')`.
                           Egyébként: `doneCb(ok, statusCode, responseBody)`.
                           HTTP hiba: `cLog` + opcionális **opts.onError**.

    Automatikus embed
      Ha `title` / `description` / `putField` / `footer` / `color` / `url` /
      `timestamp` / `author` / `thumbnail` / `image` hívás **putEmbed nélkül**
      történik, a modul **létrehoz egy embedet** (korábbi `embedId == 0` nil
      index elkerülése). A **putEmbed()** továbbra is explicit több embedhez.

    Hibák / viselkedés
      HTTP nem 2xx: `cLog` a státusz + válasz rövidített szövegével; **onError**
      callback; **send** callback `ok == false`.

    Forrás
      imports/discordlog.lua

imports – consumer / eco resource ötletek (következő lépések, nem kötelező)
  A következők **javasolt irányok** az e_core-ra épülő szkriptekhez; részben
  a `createDiscordLog` + `cLog` köré szervezhetők, részben külön modul / export.

  Strukturált szerverlog
    Egységes mezők: `resource`, `event`, `source` / azonosító, `payload` –
    fájl, külső log szolgáltatás, vagy Discord `send` előtt normalizált JSON.

  Webhook rate-limit / sor
    Sok embed vagy burst küldés esetén Discord **429** – FIFO várakozás,
    válasz `retry_after` (ha elérhető) vagy fix backoff.

  Audit export / közös minta
    Admin események (craft, trade, wipe): ugyanaz a Discord építő + `timestamp`
    + `author` / `footer` (pl. `/tp` koordináta), egységes színek (`color`).

  Trace / request id
    Kliens → szerver callback egy rövid **korrelációs id**; `cLog` és Discord
    mező ugyanazzal – összekapcsolható napló a két oldalon.

  Config-validátor induláskor
    Kötelező mezők, típus, webhook URL – egy helyen **hiba / figyelmeztetés**,
    elkerülve a futás közbeni `false` logger objektumot (ha a webhook mégis
    hibás volt).

  safeCall(tag, fn) jellegű segéd
    `pcall` + egységes `cLog` + opcionálisan kritikus hibánál Discord
    **onError** / külön admin webhook.

  Feature flag / ConVar
    Pl. `e_core:*` vagy saját convar: Discord craft log ki/be prod-ban,
    extra HTTP nélkül kód deploy.

libs/meta.lua (shared)
  Szerep
    **Proficiency szint** (`Config.levels[].limit` küszöbök szerint) és
    **kedvezmény interpoláció** (`getDiscounts`); szerver meta módosításkor
    szintváltás értesítés (`messageIfLevelChange` → `e_core:levelChange`).
  Függőség
    `local hf = hf` – a helper már betöltött; `getDiscounts` a szint sorok
    másolásához **`hf.shallowCopy`** (`libs/helper.lua`).

  Név: checkMetaExists
    Oldal: shared fájl; **hívás:** szerver (server/meta.lua), mert `ECO.meta`
      a szerveren töltődik (server/main.lua: `ECO = {}`).
    Paraméterek: playerId (number), category (string), name (string).
    Vissza: boolean – false, ha hiányzik a játékos meta sáv vagy a proficiency
      nem szám.

  Név: getLevel
    Oldal: shared; export: client + server (`getLevel` – lásd szekció 2).
    Paraméter: value – elért pontszám (number); nem szám vagy < 1 → **0**.
    Vissza: szint index **0 … (#levels - 1)**; logika: az első olyan i, ahol
      `levels[i].limit > value`, vissza **i - 1**; ha egyik küszöb sem nagyobb,
      `#levels - 1`. Üres `Config.levels` → **0**.

  Név: checkLevelChange
    Oldal: shared (szerver meta.lua hívja).
    Paraméterek: baseValue, newValue (number).
    Vissza: **false**, ha nincs változás vagy invalid; egyébként **true**,
      baseLevel, newLevel (multi-return).

  Név: messageIfLevelChange
    Oldal: shared; **csak szerver** kontextusban értelmes (TriggerClientEvent).
    Paraméterek: playerId, category, name, baseValue, newValue.
    Viselkedés: ha `checkLevelChange` true → `e_core:levelChange` payload
      (category, name, baseLevel, newLevel).

  Név: getDiscounts
    Oldal: shared; export: client + server.
    Paraméter: value – pontszám (number); `tonumber` fallback 0.
    Vissza: kedvezmény **tábla** (level, progress, limit, mezők interpolálva)
      VAGY **false, 'not_levels_data'** ha `Config.levels` üres.

    `the_system_is_turned_off`, `not_found_metadata`, `not_valid_amount`,
    `has_already_reached_the_limit` (labor limit / üres érték esetek).

Labor, meta sync, „laboros” consumer művelet – átfogó összefoglaló (support / AI)
  Részletes levezetés, táblázatok, külső kód-idézetek:
    **docs/LABOR_KEZELES_MUNKAFIL_HU.md**
  Szerveren tipikus sikeres akció (pl. craft, halászat catch) e_core oldala:
    1) **Ellenőrzés (0 e_core → kliens hálózat):** `getLabor(playerId)`,
      szükség szerint `getAbility`, `getDiscounts(proficiency)`; a fizetendő
      munkapont kanonikus formában: `base` alapköltség, `p` = kedvezmény % a
      `getDiscounts(...).labor` mezőből (0–100), majd
      `paidLabor = math.max(0, math.ceil(base * (1 - p/100)))` (ekvivalens:
      `ceil(base - (base/100)*p)`). Összehasonlítás: `getLabor` < `paidLabor` →
      hiba, nincs levonás.
    2) **Levonás + jártasság:** `removeLabor(playerId, paidLabor)` majd gyakran
      `addAbility(..., paidLabor)` – mindkettő `syncRequest(playerId)`-et hív;
      ugyanarra a `SetTimeout(0, …)` kötegre jellemzően **egyetlen**
      `TriggerClientEvent('e_core:sync', id, ECO.meta[id])` (ECO.idsToSync).
    3) **Payload:** a teljes `ECO.meta[playerId]` tábla megy, **nem** delta –
      okok: egy pillanatképes szerződés, kliens–NUI konzisztencia, egyszerűbb
      mint részleges merge (részletek + mermaid: a munkafájl „Miért teljes meta”
      fejezete).
    4) **Kliens:** `e_core:sync` → `ECO.meta` felülírás; ha NUI kész: egy
      `SendNUIMessage` UPDATE (page vagy hud), teljes `metadata`.
    5) **Auto labor:** `server/labor.lua` `laborIncrease()` tick után
      **`syncRequest(playerId)`** (ugyanaz a kötegelt útvonal, mint a meta
      írásnál); részletek: `docs/LABOR_KEZELES_MUNKAFIL_HU.md` fókuszlista.
    6) **Külső resource** (eco_crafting, eco_fishing stb.) saját eseményei,
      callback válaszok, inventory – **plusz** hálózat; nem helyettesítik az
      e_core meta sync-et.
  Kliens előellenőrzés (pl. craft UI): `getLabor()` / `getAbility` / getDiscounts
    a cache-ből – **0** e_core hálózat; a szerver újraszámol (hiteles).
  Jövőbeli egységesítés (ötlet): egy export vagy lib segéd, pl.
    `computePaidLabor(baseLabor, proficiencyPoints)` – a munkafájl „kanonikus
    labor-költség” és „Jövőbeli e_core segédfüggvény” része.

--- Client (client/exports.lua) ---

getAbility(category, name?)
  category: string, pl. crafting, reputation…
  name:      opcionális string, pl. weaponry, cooking…
  Vissza:    ha name megvan: szám (proficiency) VAGY false, hiba string
             (pl. category_does_not_exist, meta_does_not_exist).
             ha name nincs: az egész kategória tábla.

getMeta(meta?)
  meta: opcionális string kulcs.
  Vissza: egy meta részfa VAGY teljes ECO.meta (kliens cache a szerver sync után).

getLabor()
  Vissza: ha labor ki van kapcsolva Config.systemMode.labor alatt:
          false, eCoreErr.the_system_is_turned_off
          ha még nincs labor blokk a kliens cache-ben (sync előtt / üres meta):
          false, eCoreErr.not_found_metadata
          egyébként: ECO.meta.labor.val (szám).
  Forrás: `client/main.lua` `getLabor`.

isReady()
  Paraméter: nincs.
  Vissza: `true` **csak** ha `eCore:isReady() == true` (item registry kész);
          egyébként `false` (töltés vagy timeout után is).
  Megjegyzés: `eCore:isReady()` a globális `CORE_READY`-t adja (nil / false / true);
          export explicit `== true` (lásd `bridge/global/shared.lua`).

getLevel(value)
  value: elért pontszám (szám).
  Vissza: szint index (0…), Config.levels alapján. Lásd libs/meta.lua.

getDiscounts(value)
  value: pontszám.
  Vissza: kedvezmény tábla a szinthez, vagy false, 'not_levels_data'.

--- Server (server/exports.lua) – mindhez kell playerId = source vagy explicit ---

getAbility(playerId, category, name)
  **name kötelező** a szerveren (egyetlen proficiency mező); nincs „teljes kategória”
  olvasás itt – kliens `getAbility(category)` név nélkül másképp viselkedik.
setAbility(playerId, category, name, value)
addAbility(playerId, category, name, value)
removeAbility(playerId, category, name, value)
  Gyakori hiba visszatérés: false, 'not_found_metadata'
  Limit: Config.abilityLimit; lehet false, 'has_already_reached_the_limit'

getLabor(playerId) / setLabor(playerId, amount) / addLabor / removeLabor
  Labor kikapcsolva: false, 'the_system_is_turned_off'
  Érvénytelen amount: false, 'not_valid_amount'
  Meta hiány: false, 'not_found_metadata'

registerMeta(playerId, category, defaultValue)
  Új meta kategória alapértelmezett kulcsokkal; meglévőnél opcionálisan tölti
  a hiányzó mezőket.

getMeta(playerId, meta?) / setMeta(playerId, meta, value)
  setMeta: teljes kategória tábla cseréje (value); sync a kliensnek.

getLevel / getDiscounts – shared logika, szerver oldalon is exportálva.

isReady()
  Paraméter: nincs.
  Vissza: mint a kliensen – `true` csak sikeres item registry után.

getDbSchemaVersion()
  Paraméter: nincs.
  Vissza: szám – alkalmazott migrációk közül a legnagyobb `id` (`e_core_migrations`);
    **0** ha üres tábla vagy lekérdezés sikertelen (indulás előtt ne hívd megbízhatóan).

getProfessionRegistry()
  Paraméter: nincs.
  Vissza: `true, registry` ahol `registry = { [category] = { [name] = row } }`,
    `row` tipikusan: `enabled`, `displayName`, `levelProfileKey`, `maxProficiency`,
    `profile = { profileKey, displayName, mode, levels }`.
  Hiba: `false, 'profession_registry_unavailable'`.

isValidProfession(category, name)
  Paraméter: `category`, `name` (nem üres string, trimelve).
  Vissza: `true, boolean` (csak létező + engedélyezett profession ad true-t).
  Hiba: `false, 'no_valid_meta_name'` vagy `false, 'profession_registry_unavailable'`.

getProfessionDefaults(category)
  Paraméter: `category` (nem üres string, trimelve).
  Vissza: `true, { [professionName] = 0, ... }` az adott kategória engedélyezett
    professionjeiből.
  Hiba: `false, 'profession_category_not_found'` vagy `profession_registry_unavailable`.

getProfessionLevelProfile(category, name)
  Paraméter: `category`, `name`.
  Vissza: `true, { profileKey, displayName, mode, levels }`.
  Hiba: `false, 'profession_not_found'` | `profession_profile_not_found` |
    `profession_registry_unavailable`.

5. GYIK (gyakori kérdések – audit után kitöltve; bővíthető)
================================================================================

K: Mi a különbség a `docs/PUBLIC_API_HU.md` és ez a fájl között?
A: A **PUBLIC_API** a szerződés **táblázata** (exportok, `eCore:` névsor,
  `eCoreErr` tábla, deprec). Az **AI_SUPPORT_REFERENCE** a **magyar** kontextus:
  mappa szerepek, indulás, labor/meta forgalom, override stratégia. Eltérésnél
  a Lua forrás + PUBLIC_API mérvadó a névlistában; itt a narratíva.

K: Az indulási logban `items=timeout` – mit csináljak?
A: A szerver/kliens item registry **nem** töltődött be a ConVar időkorlátig
  (`e_core:items_ready_timeout_ms`). Ellenőrizd: core indulás **e_core előtt**,
  inventory override `getRegisteredItems` láncolat, `ox_lib` fut-e. Részlet:
  szekció **1.4** `server/main.lua`, **SZERVER_OPERATOR_CHECKLIST_HU.md**.

K: `exports.e_core:isReady()` mikor `true`?
A: Csak ha a registry szál sikeresen befejeződött (`CORE_READY == true`). Timeout
  után `false` marad; töltés közben is `false` (vagy belsőleg `eCore:isReady()`
  lehet `nil`). Lásd `libs/helper_ecore.lua` `awaitItemRegistryReady`.

K: Kliensen `getLabor()` ad `false, not_found_metadata` – hiba?
A: Nem feltétlenül: **sync előtt** vagy üres kliens meta esetén várható. A szerver
  újraszámol; UI-ban ne kezeld fatális hibának első frame-ben. **1.4** labor
  összefoglaló, `LABOR_KEZELES_MUNKAFIL_HU.md`.

K: Két core fut (ESX + QB) – miért áll le az e_core?
A: `e_core:framework=auto` szándékosan **error** – egy szerveren egy legacy core.
  Állítsd a ConVart `esx` vagy `qb`-ra, és távolítsd el a felesleges core-t.
  **Keretrendszer-felismerés** szekció, `FRAMEWORK_CONFIG_REFACTOR_TERVEZES_HU.md`.

K: `e_core:createVehicle` – hogyan hívjam kliensről?
A: **Ne** `TriggerServerEvent('e_core:createVehicle')`-et várj: **callback** az
  aktív bridge `eCore:createCallback('e_core:createVehicle', …)` útvonalon;
  forrás ellenőrzés a szerveren. **`docs/NET_EVENTS_AUDIT_HU.md`**.

K: Hol írjam át az ox_inventory viselkedést?
A: **`standalone/overrides/ox_inventory/`** – ne a `bridge/` tömeges forkja;
  a manifest glob sorrendje dönti el, melyik override nyer. **1.3**, stack:
  `SUPPORTED_STACK_MATRIX_HU.md`.

K: `e_core:playerLoaded` kliensről `TriggerServerEvent` – működik?
A: **Nem** (szándékos): csak szerver `TriggerEvent` + `AddEventHandler`. Régi
  külső script ilyen hívása nem fut; lásd **NET_EVENTS** doksi, `changelog` 0.0.14.

K: Mi az `e_core_migrations` tábla?
A: Az e_core **alkalmazott DB migrációinak** nyilvántartása (Fázis 3). Induláskor
  `e_core_run_db_migrations()` létrehozza, majd soronként futtatja a `#1`, `#2`, …
  lépéseket. Részlet: **`docs/DB_MIGRATIONS_HU.md`**, export: `getDbSchemaVersion`.
